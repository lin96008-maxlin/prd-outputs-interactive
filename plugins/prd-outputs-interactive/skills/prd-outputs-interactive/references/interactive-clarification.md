# 交互式需求澄清

仅在已有材料无法支持关键业务决策时读取。本能力用于减少来回追问，不替代需求分析。

## 何时提问

先完整读取用户本轮材料，合并同义缺口并删除材料已有答案。只有答案会改变范围、核心流程、角色责任、权限、数据口径、外部集成、验收方式或主体结构时才提问。

- 没有关键缺口：直接继续分析或撰写。
- 1–3 个关键问题：优先使用当前平台的原生用户提问能力。
- 4–20 个相互关联的关键问题：调用 `open_prd_clarification_questionnaire`。
- 超过 20 个候选问题：按返工风险排序，只保留最关键的 20 个；答案提交后，仅在出现新的真实冲突时追加下一轮。
- 用户要求直接输出、不追问或先给草稿：不调用问卷，说明风险并标为“待确认”。

不要为了使用问卷而制造问题，不询问低风险文案、实现偏好或可由现有材料推导的事项。

## 问题结构

每题必须包含稳定 `id`、简短 `prompt`、输入类型和是否必填。可补充 `section` 与 `description`，但不要写成长篇背景。

支持的类型：

- `single`：2–8 个互斥选项；
- `multi`：2–8 个可多选选项；
- `short-text`：名称、范围、指标等短答案；
- `long-text`：场景、规则、例外等需要解释的答案。

选项使用稳定 `value` 与面向用户的 `label`。问卷框架为单选题增加“填写其他答案”；多选题尚未选择预设项时显示“其他答案”，选择至少一个预设项后自动改为“补充说明”。AI 不要在 `options` 中重复生成这些选项。单选题选择“填写其他答案”后必须填写内容；多选题可在已选项之外追加补充说明。

显示规则：每题只展示序号、问题、选项和选项说明；不展示问题类型、分类或问题说明。问题使用 `16px`，正文和选项使用 `14px`，序号、进度等辅助信息使用 `12px`。问题和选项使用常规字重，不加粗。问题、选项及选项说明自然换行，不截断。所有选择题均使用单列选项，避免因选项数量或文字长度造成布局跳变。`short-text` 与 `long-text` 都使用可换行、随内容自动增高的多行输入框；超过最大高度后仅输入框内部纵向滚动。

## 调用与继续

调用 MCP 工具时传入：

- `title`：本轮澄清主题；
- `contextSummary`：已知事实和为什么需要本轮确认，最多 300 字；
- `questions`：按决策顺序排列的问题，最多 20 个。

支持 MCP Apps 的宿主会在对话中显示问卷。用户提交后，答案通过 `PRD_CLARIFICATION_ANSWERS` 上下文和一条用户消息回到当前对话。收到后：

1. 按 `questionId` 将答案合并进事实基线；
2. 区分已确认、仍待确认和用户跳过的内容；
3. 不复述整份问卷，只总结改变需求判断的答案；
4. 继续原分析或 PRD 流程。

不支持 MCP Apps 的宿主仍会收到文本版问题。此时使用平台原生提问能力分批询问；没有原生能力时输出编号问题并等待用户回复。UI 不可用不能阻断 PRD 能力。

## 数据边界

- 本地 MCP Server 不把问题或答案写入磁盘。
- 问卷答案只进入当前会话上下文；是否发送给模型取决于宿主平台本身。
- 不收集密码、密钥、身份证件、支付信息等敏感凭据。
- 用户关闭或取消问卷时保持现有事实基线，不自行补答案。

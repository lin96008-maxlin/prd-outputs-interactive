# PRD 文件管理规则

## 1. 优先顺序

1. 用户指定的目录、文件名和项目规则优先。
2. 更新已有 PRD 时直接修改当前有效文件，不擅自改名或复制第二份主稿。
3. 全新任务且用户未指定位置时，使用本文件的默认结构。

不得把项目产物写入 Skill、Plugin、全局资料或其他项目目录。

## 2. 默认结构

```text
requirements/
└── <需求主题>/
    └── <YYYYMMDD><需求主题>PRD-v1.md
```

需求主题应简短、可识别，保留必要中文，不使用“最终版”“最新版”等无法长期维护的词。

文件名规则：

- `YYYYMMDD` 使用创建当天日期，不加分隔符；
- 日期与需求主题之间不加连接符或空格；
- 固定使用大写 `PRD`；
- 首次创建固定使用 `-v1`；
- Markdown 扩展名为 `.md`。

示例：

```text
requirements/任务中心移动端/20260901任务中心移动端PRD-v1.md
```

若项目已有 `docs/`、`product/`、`requirements/` 或其他正式文档目录，沿用项目结构，不额外套一层目录。

## 3. 唯一主稿

- 同一需求只维护一份主 PRD。
- 版本、日期、状态和负责人写在文档元信息中，不依靠复制文件表达版本。
- 后续变化直接更新正文，并在确有追溯需要时补一条变更摘要。
- 分期在同一 PRD 中通过阶段、范围和优先级表达，不为每一期复制一份主稿。

## 4. Word 导出

用户明确要求 Word 时，在主稿旁导出同名文件：

```text
requirements/<需求主题>/<YYYYMMDD><需求主题>PRD-v1.md
requirements/<需求主题>/<YYYYMMDD><需求主题>PRD-v1.docx
```

Markdown 是唯一维护主稿，DOCX 只用于评审或归档。后续先更新 Markdown，再重新导出 DOCX，不分别维护两套正文。

若用户只提供现有 DOCX 且未允许覆盖，保留原件，并在用户指定位置保存派生文件。

## 5. 辅助文档

只有长期接力、材料复杂或质量检查需要留痕时才创建：

```text
requirements/<需求主题>/handoff.md
requirements/<需求主题>/quality-record.md
requirements/<需求主题>/project-constraints.md
requirements/<需求主题>/document-index.md
```

辅助文档分别记录交接、检查结果、共同约束或材料索引，不承载第二套需求规格。

## 6. 特殊情况

- 多个输入文件：优先使用用户指定的主材料；无法确定时按需求主题建目录，不拼接多个文件名。
- 多个候选 PRD：按用户指定、文档状态和内容一致性判断当前主稿；无法判断时只确认这一项。
- 多个需求合并：形成统一范围时使用一个主题；仍是独立范围时分别维护。
- 项目已有版本控制：遵守项目规则，不另建平行版本。

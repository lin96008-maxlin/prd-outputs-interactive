# PRD 分析检查项

## 使用规则

本文件帮助 AI 检查是否遗漏重要规格，不是必须逐项输出的问卷或固定章节。

- 只读取与当前需求有关的部分。
- 用户指令和当前有效材料优先。
- 没有依据的字段、状态、角色、规则和指标不得补成事实。
- 材料只列出字段但没有声明必填、默认值或可编辑角色时，保持未定义，不根据常见做法推断。
- 材料提到的操作必须对应角色、前置状态和结果；缺少条件时进入待确认项，不能从规格中消失。
- 批量条件不等于批量失败策略，指标名称不等于计算公式；材料未给出时分别标为待确认或建议口径。
- 最终 PRD 按业务内容组织，不按本文件顺序堆砌。
- 只有会改变范围、责任、核心规则或验收的缺口才需要询问。

## 1. 事实与决策

### 材料状态

- 当前有效：可以支撑当前需求。
- 历史参考：用于理解背景，不能覆盖当前口径。
- 待确认：仍需责任角色确认。
- 已失效：不再作为当前依据。

### 内容性质

- 事实：材料或系统可以直接证明。
- 决策：责任角色已经确认的选择。
- 假设：为了继续分析暂时采用，需要明确影响。
- 建议：可供选择但尚未生效。
- 分歧：不同有效来源给出不同结论。

待确认内容应说明影响范围、决策角色、下一步和是否阻断，不只放一个状态标签。

## 2. 参与者与使用条件

按需区分：

- 提出需求的人；
- 直接使用系统的人；
- 使用结果但不直接操作的人；
- 因权限、流程、数据或工作方式变化而受影响的人；
- 负责确认、审批、监督或承担结果责任的人；
- 外部机构、客户、供应商或其他系统。

使用频率、设备、网络、操作熟练度、既有习惯和风险敏感度只有在改变操作路径、默认值、提示、防错、兼容或恢复要求时才进入 PRD。

## 3. 对现有能力的影响

分别判断三个方面，不合并成一组选项。

### 当前能力如何变化

- 保持：现有能力已经满足需求。
- 调整：保留现有主体，修改规则、入口、组合、权限或呈现。
- 新增：现有能力无法承载，需要增加。
- 停用：当前能力退出，需要说明兼容、迁移和回退。
- 待确认：证据不足，不能下结论。

### 规则适用于哪里

- 公共能力：多个稳定场景共同使用。
- 租户或项目规则：只在明确范围内生效。
- 待确认：使用边界尚未明确。

### 规则是否可配置

- 固定规则：无需业务人员动态维护。
- 可配置：差异稳定、取值有限、存在明确维护角色。
- 待确认：配置对象或维护责任不清楚。

配置项必须说明配置对象、维护角色、取值范围、生效范围、生效时机和历史数据处理方式。

## 4. 权限与职责

权限按实际需求检查：

1. 功能权限：模块、菜单、页面或入口能否访问。
2. 操作权限：查看、新增、编辑、删除、提交、审批、导入、导出等动作能否执行。
3. 数据权限：可以查看或处理哪些组织、团队、本人或被分配对象的数据。
4. 字段权限：字段可见、可编辑、只读、隐藏或脱敏。
5. 状态限制：对象处于特定状态时允许哪些操作。

处理、复核、审批、监督、配置和异常兜底属于职责，不要与权限混写。一个人拥有多个角色时，按需说明权限合并、冲突优先级和最终数据范围。

## 5. 字段与数据

字段较多或规则复杂时使用字段表：

| 内部名称 | 显示名称 | 类型 | 必填 | 默认值 | 取值 / 校验 | 数据来源 | 可编辑角色 | 数据范围 | 脱敏 / 隐藏 | 空值处理 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |  |  |  |  |  |

按需补充长度、精度、单位、唯一性、是否可重复、级联、排序、搜索、导入导出和历史值兼容。

数据口径至少检查：

- 权威数据源；
- 统计对象和纳入范围；
- 时间窗口和时区；
- 去重、排除和修正规则；
- 刷新频率和延迟；
- 权限范围；
- 历史数据如何处理。

## 6. 状态与流程

状态不能只列名称，还应说明由什么事件、什么角色、在什么条件下发生变化。

| 当前状态 | 触发事件 | 执行角色 | 前置条件 | 下一状态 | 成功结果 | 失败 / 退出方式 |
| --- | --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |  |

按需检查：初始和终止状态、可逆性、撤回、退回、关闭、重新开启、超时、自动处理、人工补偿、并发、重复提交、通知、日志和权限变化。

## 7. 操作与反馈

常见操作包括查看、搜索、筛选、排序、新增、编辑、删除、恢复、提交、审批、转办、导入、导出、上传、下载、批量处理、配置和启停。

每个重要操作按影响说明：

- 谁可以执行；
- 在什么条件下可执行；
- 影响哪些对象和数据；
- 成功后用户看到什么；
- 失败或受限时原因和下一步是什么；
- 是否支持撤销、恢复或重试；
- 是否需要确认或审计记录。

部分成功必须分别说明成功项、失败项、失败原因和重试方式。

## 8. 异常与边界

按需检查：

- 默认、空、加载、错误、禁用和无权限；
- 数据已删除、已变化或已被他人处理；
- 未保存离开、网络中断、超时和重试；
- 重复提交、重复数据、并发冲突和部分成功；
- 上传失败、格式错误、数量或大小超限；
- 外部系统不可用、接口异常和数据延迟；
- 存量数据兼容、历史字段缺失和迁移失败；
- 查询无结果、筛选冲突和权限导致的数据为空。

## 9. 验收

验收覆盖与当前需求相关的维度：

- 功能：主路径是否完成并产生正确结果；
- 权限：功能、操作、数据、字段和状态边界是否正确；
- 数据：来源、计算、刷新、去重和范围是否正确；
- 状态：变化条件、结果、可逆性和异常路径是否正确；
- 异常：空、错误、超时、重复、并发和部分成功是否可处理；
- 质量：性能、兼容、可用性、日志、监控和安全是否达到已确认要求；
- 发布：存量数据、灰度、回退、通知和历史兼容是否闭合。

每个关键验收场景至少包含对应需求、角色、前置条件、测试数据、操作或触发、可观察结果和异常分支。

一条场景尽量只验证一个主要结果。字段长度、附件类型/大小/数量、通知接收人、跨组接受与拒绝、状态时间边界和越权访问分别覆盖。公开回复、内部处理记录等副作用不同的动作必须分开定义和验收。

没有事实依据时，不编造性能数字、合规等级、保留期限或容量目标。

## 10. 变更影响

已有 PRD 或既有系统发生变化时，按需检查：

- 变更原因；
- 当前行为；
- 新行为；
- 受影响的角色、页面、流程、接口、字段、状态和数据；
- 兼容、迁移、培训和回退；
- 对应验收是否同步更新。

稳定的新行为必须写回正文。变更记录只负责帮助追溯，不能代替当前规格。

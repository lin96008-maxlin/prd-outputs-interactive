# 原型反馈与 PRD 更新

仅在用户基于原型、系统走查、开发结果或多轮反馈继续更新 PRD 时读取。普通新建 PRD 不需要加载本文件。

## 1. 各类材料负责什么

- 用户当前指令：决定本轮变更和例外。
- 主 PRD：保存已经稳定的需求、规则和验收，是唯一需求主稿。
- 原型：展示已经确认的页面结构、状态和交互，不负责改变业务边界。
- 真实系统或源码：证明当前已有页面、接口、字段、状态、权限和操作。
- 交接文档：记录当前有效文件、读取顺序、完成情况和下一步。
- 质量记录：记录检查方法、问题、证据和修复状态。
- 历史材料：帮助理解背景，不能自动覆盖当前结论。

不要只凭文件更新时间判断业务口径。

## 2. 用户反馈如何处理

| 反馈内容 | 主 PRD 如何更新 | 其他记录 |
| --- | --- | --- |
| 名称或业务术语变化 | 全文统一当前名称 | 需要交接时同步更新基线 |
| 功能、规则或范围缺漏 | 补入对应详细需求 | 验收场景同步调整 |
| 原型出现无依据能力 | 从当前规格中纠正，或明确为新增需求 | 质量记录可保存检查结果 |
| 权限、字段、状态或数据变化 | 更新对应需求和全局规则 | 必要时增加影响说明 |
| 当前有效原型变化 | 需求含义变化时回写正文 | 交接文档记录有效文件 |
| 实现缺陷但需求未变 | 主 PRD 不变 | 写入质量记录 |

更新记录只写本次变化摘要。当前有效规则必须出现在正文，不能要求读者通过历史记录拼出现在应该怎么做。

## 3. 页面和交互相关需求

当需求主要由页面和交互承载时，按需写清：

- 页面或入口属于哪个功能；
- 默认打开内容、筛选、排序、展开和选中状态；
- 用户需要看到的信息、字段和状态；
- 主要操作、辅助操作、批量操作和不可用条件；
- 搜索和筛选如何组合；
- 列表、详情、编辑、步骤、时间线或画布如何承载业务；
- 只读与可编辑内容的差异；
- 页面切换、联动和返回时保留哪些状态；
- 空、加载、错误、禁用、无权限、删除确认和未保存离开如何处理；
- 保存、取消、关闭、删除和开关操作如何完成闭环；
- 演示数据来自什么口径，哪些内容不能伪造。

具体组件和视觉形态只有在用户、原型或项目规范明确时才进入 PRD，不依据个人偏好补写。

## 4. 既有系统调整

任务明确涉及现有产品、开源项目或源码时，对相关页面、接口、字段、状态、权限和操作逐项记录：

- 保持：现有能力符合当前需求；
- 调整：保留主体，但改变规则、入口、组合或边界；
- 新增：现有能力无法承载；
- 停用：当前能力退出，需要兼容、迁移或回退；
- 待确认：证据不足。

不要把设计方案写成系统已经具备的能力，也不要因为希望体验更好就补出后端字段或接口。

## 5. 变更影响

以下变化通常需要同步检查正文和验收：

- 名称、字段、状态、权限和数据口径；
- 页面归属、入口和功能范围；
- 流程条件、责任角色和异常处理；
- 外部系统边界和接口方向；
- 兼容、迁移、培训、灰度和回退。

只有真实影响当前系统时才写变更前后的对照。被放弃的方案不进入当前规格，也不在标题或注释中留下处理痕迹。

## 6. 更新节奏

1. 开始前读取当前主 PRD、当前有效产物和必要依据。
2. 进行中记录用户新增决策、原型暴露的需求缺项和系统核对结果。
3. 结束时把稳定结论写回主 PRD，把检查过程写入质量记录，把有效文件和下一步写入交接文档。
4. 进入下一范围前重新确认当前主稿和有效产物，避免使用历史文件。

## 7. 跨会话接力

需要换会话继续时，最少说明：

- 当前唯一主 PRD；
- 当前有效原型或其他产物；
- 历史文件的用途和状态；
- 已确认术语、范围和业务约束；
- 已完成、未完成和阻断内容；
- 开始工作前的读取顺序；
- 下一步及责任角色。

后续接手者应只读这些文档即可继续，不依赖聊天记录还原需求。

## 8. 更新前检查

- 用户最新反馈是否进入对应详细需求；
- 当前有效原型或系统证据是否清楚；
- 页面、详情、编辑和辅助入口的归属是否正确；
- 既有系统判断是否有证据；
- 变更影响和验收是否同步；
- 当前正文是否只描述现在需要实现和验证的内容；
- 后续接手者是否能够直接继续。

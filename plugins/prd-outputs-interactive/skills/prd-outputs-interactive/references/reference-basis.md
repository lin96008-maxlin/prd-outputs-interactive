# PRD 公开方法依据

## 使用目的

本文件仅在用户询问 PRD 方法来源、标准依据或验收写法时读取。公开方法用于帮助组织需求和检查质量；当前项目的角色、字段、流程、规则、指标和技术方案仍以本次有效材料为准。

## 方法来源

| 来源 | 适用方法 | 在本技能中的使用 |
| --- | --- | --- |
| [Atlassian Product requirements template](https://www.atlassian.com/software/confluence/templates/product-requirements) | 目标、假设、范围、优先级、成功指标、开放问题和单一事实来源 | 组织主 PRD 的概述、范围、假设、优先级和开放问题 |
| [GOV.UK Writing user stories](https://www.gov.uk/service-manual/agile-delivery/writing-user-stories) | 从用户、场景、问题和目标出发；用可观察结果验收 | 组织问题证据、目标结果和验收场景 |
| [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 与 [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) | 区分强制、推荐和可选要求 | 在中文 PRD 中一致使用“必须 / 应 / 可以” |
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | 可测试的可访问性成功标准 | 项目明确存在可访问性目标时，记录版本、级别、适用范围和验证方式 |
| [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) | 可验证的应用安全要求 | 项目明确涉及安全目标时，记录标准版本、要求编号、适用资产和验证方式 |

## 采用规则

1. 公开方法决定“如何组织和验证需求”，当前材料决定“产品具体做什么”。
2. 用户故事用于概括角色、目标和价值；字段、权限、状态、异常和验收仍需结构化规格。
3. 成功指标需要当前项目的基线、目标、统计周期、口径、数据源和负责人。
4. 可访问性和安全标准按项目目标、法规或合同要求触发，并保留可定位的版本和条款。
5. 标准无法直接提供当前项目事实；证据不足的内容按风险确认或标为“待确认”。

## 条款写法

- **必须**：缺失即无法验收，或会造成不可接受风险。
- **应**：正常情况下要求满足；存在例外时说明条件和补偿方式。
- **可以**：可选能力，不实现也不影响强制要求。

约束强度应来自业务、质量、法规或合同事实，不能用强制词包装偏好。

## 标准引用格式

当 PRD 直接引用标准时，至少记录：

- 标准名称；
- 版本或发布日期；
- 条款编号或成功标准编号；
- 适用范围；
- 验证方式。

## 维护规则

- 优先使用发布机构的官方页面或固定版本页面。
- 来源更新时核对方法含义，再决定是否调整模板或检查规则。
- 标准升级时保留版本边界，不把新版本要求回写为历史项目事实。
- 来源暂时不可访问时保留已确认版本，并标记待重新核验。

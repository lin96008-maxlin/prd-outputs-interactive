## 1. 启动判断

先判断用户本轮目标：

| 模式 | 判断信号 | 默认动作 |
| --- | --- | --- |
| 分析 / 澄清 | 只要求分析、澄清或梳理，未要求形成 PRD | 直接答复，不创建文件 |
| 直接 PRD | 明确要求新建 PRD | 默认创建一份主 PRD |
| 更新 PRD | 已有 PRD 或明确有效基线 | 沿用原文件回写 |
| 治理型 PRD | 长期迭代、多来源冲突、历史材料复杂或需要接力 | 先更新主 PRD，再按需增加辅助文档 |

不询问可以从材料直接判断、已经确认或影响较低的事项。当疑问会显著改变需求范围、核心流程、角色责任、数据口径、验收方式或导致主 PRD 主体返工时，主动暂停并询问。当前主 PRD 无法识别，或增加治理文档会明显改变交付范围时，也应先确认。1–3 个关键问题使用平台原生提问；4–20 个相互关联的问题按 [interactive-clarification.md](interactive-clarification.md) 使用问卷集中收集。不得把完整检查表直接抛给用户。用户要求“直接输出 / 不要追问 / 先给草稿”时，说明风险并将缺口标为“待确认”后继续。

开始写文件前：更新已有 PRD 时沿用原路径和文件名；全新创建时按 [naming-and-files.md](naming-and-files.md) 建立需求目录和主 PRD。

建立最小来源清单，至少记录“来源是什么、是否当前有效、支持哪些事实、存在什么冲突”。来源较少时可直接写在主 PRD；来源复杂时再使用来源追溯矩阵。

## 2. 模式与规格组合

### 直接 PRD

用于来源较少、周期较短、交接不是重点的任务。默认只产出 1 份主 PRD。
直接 PRD 可以压缩表达，但不能省略来源、冲突口径、待确认项、关键假设和验收口径。

### 治理型 PRD

用于长期迭代、多来源冲突、历史材料复杂或后续需要跨会话接力的任务。除主 PRD 外，可按需补辅助文档。
治理型任务必须先锁定并更新唯一主 PRD，再按需更新辅助文档；不得用交接文档、质量记录或项目约束文档替代主 PRD。

### 规格组合

所有 PRD 使用同一骨架。根据需求事实，在对应需求单元中选取必要内容：

- **交互承载**：入口、可见信息、操作、反馈和状态呈现；
- **流程行为**：触发、条件、分支、状态变化、通知和恢复；
- **数据规则**：业务对象、字段、来源、计算、保存和权限范围；
- **集成约束**：外部系统、数据方向、调用时机、失败责任和降级；
- **交付影响**：存量兼容、依赖、迁移、灰度、回退和文档更新。

同一需求单元可以组合多个方面。不要为了匹配模板把一个业务需求拆成多份规格，也不要在文档开头声明“属于哪一种类型”。

## 3. 文档角色

默认只维护主 PRD。辅助文档只在必要时补充，且不能承载另一套需求事实。

唯一主 PRD 锁定顺序：优先用户明确指定；其次采用交接 / 控制文档声明的当前主 PRD；再次采用最新标记为有效 / 已确认的正式 PRD。若仍冲突，只问一个基线确认问题，不自行合并出第二套主稿。

| 文档 | 何时使用 | 承载内容 | 不承载内容 |
| --- | --- | --- | --- |
| 主 PRD | 默认必有 | 稳定需求事实、功能规格、验收口径 | 会话流水账 |
| 交接 / 控制文档 | 长期接力、历史材料复杂、跨会话接手 | 当前阶段、有效基线、已确认约束和读取顺序 | 详细产品规格 |
| 质量记录 | 阶段验收、走查、审查确有必要 | 检查结果、问题、修复状态 | 新需求事实 |
| 项目约束文档 | 跨页面、跨模块、跨团队门禁确有必要 | 执行约束、红线、验收门禁 | 业务规格细节 |
| 文档索引 | 材料非常多时 | 当前有效文档、历史材料、阅读顺序 | 产品规格 |

## 4. 内部收敛流程

以下动作在一次工作流中连续完成，不生成中间文档，也不要求用户逐段确认：

1. **整理事实与决策**：区分有效证据、已确认决策、待确认决策、假设和来源分歧。
2. **确定边界与能力**：说明本期范围、参与者、业务对象、能力及上下游关系。
3. **形成需求单元**：为关键需求分配稳定 ID，把当前有效规则和受影响维度写入同一单元。
4. **连接公共约束**：权限、数据、状态、依赖或发布规则被多个需求共用时集中记录，避免重复。
5. **连接验证**：建立 `REQ → 证据 → 当前规格 → 验收场景` 的可检查关系。
6. **合并主稿**：把稳定结论写回唯一主 PRD，清理空章节、重复说明和失效内容。

只有阻断性决策缺失时暂停；用户答复后继续当前工作流。已确认内容直接进入主稿，不单独保留阶段稿。

## 5. 需求准确性门禁

在整理材料和编写规格时持续执行轻量检查。与本次任务相关但无法确认的内容，按影响处理：

- **高风险**：错误假设会改变范围、核心流程、角色责任、数据口径、验收方式或导致主 PRD 主体返工时，主动询问。
- **中低风险**：允许根据已有材料和可靠证据形成判断；无依据则标为“待确认”。
- **展示性低风险**：可作为假设或展示示例，但需标明不是确定事实。

遇到以下业务澄清点时，不应靠猜测继续：

1. **问题证据**：无法确认受影响对象、发生环境、可观察问题或目标结果。
2. **含糊业务术语**：“灵活”“友好”“统一”等词存在多种会影响功能或验收的解释。
3. **关键业务边界**：权限、流程、状态、数据范围或异常处理边界不清。
4. **外部系统集成**：对接范围、数据方向、触发时机或责任边界不清。
5. **质量目标**：性能、并发、安全等要求会影响方案或验收，但目标口径不清。
6. **基线影响**：无法判断现有能力应保持、调整、新增还是停用。
7. **来源分歧**：关键字段、状态、动作、权限、数据或接口在有效材料中出现冲突。

以上不是固定问卷。先删除材料已有答案的问题，再按返工风险排序；单轮最多保留 20 个关键问题。原生提问或交互式问卷完成后继续原流程。用户要求“直接输出 / 不要追问 / 先给草稿”时，说明风险、标记“待确认”并继续。用户要求“完整确认 / 逐项对齐”时，才扩大提问范围。

| 门禁项 | 判断内容 |
| --- | --- |
| 问题证据 | 受影响对象、发生环境、当前可观察问题和目标结果是否有材料支撑 |
| 参与者 | 发起、使用、受益、受影响、决策和承担结果责任的角色是否已区分 |
| 使用约束 | 使用频率、设备、网络、操作熟练度或既有习惯是否真正改变规格 |
| 当前决策 | 材料中的事实、方案和已经确认的业务决策是否已分开 |
| 基线影响 | 保持 / 调整 / 新增 / 停用 / 待确认 |
| 适用边界 | 公共能力 / 租户或项目规则 / 待确认；可配置项必须有稳定差异、有限取值和维护责任 |
| 范围边界 | 做什么、不做什么、涉及哪些端 / 系统 / 模块 |
| 授权与职责 | 功能、操作、数据、字段权限是否清楚；状态是否会进一步限制操作；处理、复核、审批和兜底责任是否明确 |
| 能力边界 | 每项能力的业务对象、包含范围、排除范围和上下游是否清楚 |
| 信息优先级 | 决策必需、执行辅助和按需参考信息是否影响承载方式 |
| 数据口径 | 数据来源、统计口径、时间口径、刷新频率、去重规则、权限数据范围 |
| 验收口径 | 如何判断做对，如何验证关键路径、异常和边界 |

事实边界还需逐项检查：

- 材料没有声明必填、默认值、可编辑角色或状态前提时，不自行补成确定规则；
- 材料只给出指标名称和目标、未给计算方式时，计算公式标为建议口径或待确认；
- 材料只给批量选择条件、未给部分失败处理时，不自行决定整批失败或跳过不合规项；
- 材料提到的每个操作必须对应角色、前置状态和结果；条件缺失时进入待确认项，不能从正文消失；
- “材料已确认”不代表内部矛盾自动消失，冲突仍需显式列出。
- 多条规则能够直接相交得到唯一结论时应完成收敛，例如“某角色可重开有权工单”与“已关闭仅组长或经理可重开”共同限定该角色只能重开有权的已解决工单；这类结论不应继续标为模糊。

待确认事项按影响分级：

- **业务决策阻断**：角色、权限、状态变化、责任或核心规则缺失，相关需求不能进入验收；
- **验收口径缺口**：指标公式或边界值缺失，只阻断对应数值验收，不阻断已经明确的页面、字段和流程；
- **交付依赖**：接口、节假日、账号、环境或数据准备未就绪，影响上线或联调，不等同于业务规则未确认；
- **实现决策**：并发、部分失败、重试或补偿需要产品与技术共同确定时，先写最低业务结果，不扩大为整份 PRD 阻断。

基线影响、适用边界和可变性分别判断：

1. 基线影响：保持 / 调整 / 新增 / 停用 / 待确认。
2. 适用边界：公共能力 / 租户或项目规则 / 待确认。
3. 可变性：固定规则 / 可配置 / 待确认。
4. 只有差异稳定、取值有限且存在明确维护角色时，才定义配置项。

这里的“已有能力”只有在任务提供现有产品、历史 PRD、源码、原型或其他依据时才判断；没有依据时不要臆造。

## 6. 来源追溯分级

来源追溯用于防止把推测写成事实，但不要把普通 PRD 写成追溯审计表。

| 风险级别 | 适用内容 | 处理方式 |
| --- | --- | --- |
| 高 | 权限、状态流转、外部系统、审批责任、核心字段、验收项、既有能力来源 | 独立来源追溯矩阵或节点内显式来源 |
| 中 | 页面、流程、按钮、筛选项、默认值、数据口径 | 节点内写来源 / 确认状态 |
| 低 | 示例文案、演示数据、低影响展示内容 | 可集中说明来源或标为示例 |

确认状态建议：

- 已确认：用户或当前权威材料明确给出
- 待确认：合理推断但未确认
- 已取消：用户明确否定或历史版本作废
- 历史参考：可参考但不能覆盖当前口径

“待确认”用于尚无结论且会影响实现、验收或责任边界的内容；同时注明是否阻断以及需要谁作出决策。

来源冲突不采用一套全局线性排序，按事实类型判断：

- 用户最新明确指令：决定当前需求变更和例外。
- 当前主 PRD：唯一稳定需求事实来源。
- 源系统、接口或源码：决定已有能力、字段、状态和接口事实。
- 已确认原型：补充已经确认的呈现和交互细节，不能覆盖需求边界或伪造已有能力。
- 交接 / 控制文档：声明当前基线、读取顺序和冻结范围，不承载需求规格。
- 历史材料：只作参考，不能覆盖当前口径。

冲突处理至少给出：冲突事实、涉及来源、采用口径、采用理由、影响范围、是否需要用户决策。不能用“以最新为准”替代事实维度判断；文件时间更新不等于业务口径更新。

## 7. 主 PRD 内容组织

主 PRD 默认采用“最小必需内容 + 条件章节”结构，不保留空章节和空表。

### 默认阅读顺序

- 文档元信息；
- PRD 概览：用较短篇幅说明背景、目标、范围、角色、关键决策和来源；
- 业务流程与功能结构：让读者先看到工作如何推进；
- 详细需求及对应验收：按用户任务、业务步骤或高频工作顺序展开，是正文主体；
- 共用规则与数据：只记录被多个需求共同使用的规则；
- 验收与交付：验收场景、外部依赖、发布准备、待确认项和风险。

大型产品可在详细需求中按模块继续分章。字段、状态、页面、SLA、通知和异常优先跟随对应业务需求，不默认成为互相平行的顶层章节。内部使用的“能力地图、需求单元、基线影响”等词只用于组织和检查，不作为最终章节标题。

### 条件章节

- 成功指标：目标可衡量或涉及上线效果时
- 既有系统核对：涉及现有产品、源码或二次开发时
- 来源追溯矩阵：多来源冲突、高风险内容较多或长期维护时
- 页面状态矩阵：页面状态复杂且会改变操作或反馈时
- 默认演示数据：原型、演示或测试需要时
- 依赖与前置条件：存在外部系统、数据准备、账号权限、组织流程时
- 发布 / 迁移 / 回退：真实上线、存量系统改造或灰度发布时
- 动态更新记录：更新已有 PRD 或多轮变更时
- 变更前后对照：变更需求、既有 PRD 更新或既有系统改造影响现有口径时
- 需求追溯矩阵：新增、关键、争议或高风险需求较多时
- 完整性自检：默认内部使用；用户要求或治理型任务中可输出

强触发规则：目标可衡量时写成功指标；存在外部协同时写依赖与前置条件；真实上线或存量迁移时写发布 / 迁移 / 回退；多来源冲突或高风险内容较多时写来源追溯矩阵。

## 8. 需求单元写法

每个关键需求使用一个稳定 `REQ-###`。以下字段按实际影响选取，不保留空项：

- 目标结果、参与者、发生环境；
- 触发条件和前置条件；
- 输入、处理规则、输出和可观察结果；
- 页面入口、展示、操作和反馈；
- 流程分支、状态变化、通知和副作用；
- 权限、数据范围、字段边界和数据保存；
- 失败、受限、超时、重试、幂等、人工介入或恢复；
- 配置对象、维护角色、生效范围和生效时机；
- 证据引用、决策状态和验收场景。

页面和流程只是同一需求的不同影响面，不拆成两套规格。规则是主体时先写规则，页面仅说明如何承载；操作和展示是主体时先写用户可观察行为，跨页面规则集中到公共约束。

字段较多时使用字段矩阵；状态会改变操作时使用状态权限矩阵；操作复杂或风险较高时使用操作与反馈矩阵；多个需求共享同一规则时只在公共约束记录一次。详细枚举见 [prd-analysis-enumerations.md](prd-analysis-enumerations.md)。

## 9. 动态回写位置

| 变化类型 | 写入位置 |
| --- | --- |
| 命名、字段、状态、页面归属、功能范围变化 | 主 PRD |
| 新增 / 删除页面、辅助承载面、流程、权限、规则 | 主 PRD |
| 最新有效产物基线、读取顺序和已确认约束 | 交接 / 控制文档 |
| 一次性检查过程、证据、浏览器检查和缺陷状态 | 质量记录或阶段记录 |
| 源码核对形成的保持 / 调整 / 新增 / 停用稳定结论 | 主 PRD；检查证据可留质量记录 |
| 跨页面或跨模块执行门禁 | 项目约束文档 |
| 只修实现缺陷且无需求含义变化 | 质量记录即可，不必改主 PRD |

原型评审或开发走查中的用户反馈不是临时意见。用户纠正命名、状态、字段、归属、按钮、页面层级、既有能力边界时，都应判断是否需要回写主 PRD。
动态更新记录只记录本次回写摘要，不记录完整会话流水；稳定口径必须落到主 PRD 对应正文章节。
变更会影响现有行为、权限、数据或验收时，同时补“变更原因、当前行为、新行为、影响范围、验收更新”；正文始终呈现当前有效规格。

## 10. 既有系统 / 源码场景

只有任务涉及现有产品、源码、开源项目或二次开发时启用。
只读取与本次模块直接相关的源系统页面、路由、接口、字段、状态、权限、操作和命名，不做无关全量源码审计。

必须记录：

- 核对范围：页面、接口、路由、字段、状态、权限、操作
- 保持：源系统已经具备且语义一致
- 调整：保留主体，但需要改变规则、入口、组合或边界
- 新增：源系统没有，需要增加
- 停用：现有能力需要退出，并说明兼容、迁移和回退影响
- 证据与待确认项：记录支持结论的来源，以及当前无法判断的字段、状态、按钮或能力
- 逐项结论：页面、接口、字段、状态、权限、操作分别记录基线影响；不能只写“参考源码”

本节仅在任务明确涉及既有系统或源码时加入。

## 11. 最小自检

### 通用自检

- 是否说明受影响对象、问题证据和目标结果
- 是否区分材料中的事实、方案和当前决策
- 材料出现的业务操作是否全部落到详细需求、验收或待确认项
- 字段必填、默认值、操作角色、批量失败方式和指标公式是否有明确依据
- 是否写清范围、非范围、优先级或分期
- 是否写清相关授权、职责、数据口径、关键状态和验收口径
- 新增、关键、争议或高风险需求是否使用稳定 ID，并能追溯到来源、变更和验收
- 授权是否至少区分功能、操作、数据和字段，职责是否独立记录，用户特性是否只在影响规格时出现
- 能力的业务对象、边界和上下游关系是否说明
- 高风险内容是否有来源或标为待确认
- 是否列出假设、待确认项、风险与开放问题
- 变更需求是否同步更新正文，并在必要时保留变更前后对照
- 每个关键需求是否能定位到来源、当前规格和至少一个验收场景
- “必须 / 应 / 可以”是否表达一致，是否存在无法测试的“友好、快速、稳定、灵活”等孤立形容词

### 交互承载自检

- 是否区分入口、页面、详情、编辑、辅助承载面等归属；具体组件形态是否有来源
- 是否写清入口、默认态、筛选、主操作、详情入口、保存 / 删除 / 关闭规则
- 是否覆盖空态、加载态、错误态、禁用态、无权限态
- 是否写清只读 / 可编辑差异、联动与状态保留
- 是否写清默认演示数据的数据口径，避免随意造口径

### 流程行为自检

- 是否写清触发、输入、输出、规则、状态流转
- 是否覆盖分支、异常、失败、退出、恢复、人工介入
- 是否写清权限、日志、通知、数据保存与清理
- 是否能用测试场景验证成功、失败和边界

### 治理型自检

- 是否写清当前主 PRD 是哪一份
- 是否写清当前有效产物、基线和历史材料状态
- 是否写清读取顺序和已确认约束
- 是否保证后续接手者无需会话记忆即可继续推进

## 12. 输出质量合同

交付前逐项判断。任何关键项不满足时，修正文档；无法修正时在交付说明中显式列为缺口，不得声称已完整闭合。

| 维度 | 通过条件 | 常见不通过 |
| --- | --- | --- |
| 事实 | 关键事实有来源；推断、假设和已取消口径被区分 | 把示例、历史截图或行业常识写成当前事实 |
| 范围 | 目标、非目标、范围、非范围、优先级或分期一致 | 目标写了“提效”，却把无关功能全部纳入 P0 |
| 规格 | 关键节点能回答谁、何时、按什么规则、得到什么结果、失败怎么办 | 只有页面名、按钮名或一句用户故事 |
| 权限与数据 | 相关角色、操作、数据和字段边界可实现、可验收 | 只写“管理员可用”或“按权限展示” |
| 验收 | 关键需求有可观察结果；高风险项覆盖失败、越权或恢复 | 验收只复述功能标题，或使用“体验良好” |
| 追溯与变更 | `REQ` 可关联来源和测试；变更正文与影响同步更新 | 只追加更新日志，不修正文 |
| 可维护性 | 唯一主 PRD、术语一致、无空章节、开放问题有后续动作 | 当前主稿不唯一，待确认项无人处理 |

分析 / 澄清模式采用压缩合同：至少输出已知事实、当前决策、范围判断、关键分歧或缺口、建议决策和下一步。若某个高风险问题会改变主体结构，只问当前最关键的问题；用户要求先出草稿时继续，但保留待确认项。

## 13. 条款与验收写法

### 13.1 约束强度

参考 RFC 2119 / RFC 8174 的思想，在中文 PRD 中保持一致：

- **必须**：不可缺少，违反即不能验收或产生不可接受风险。
- **禁止 / 不得**：明确不允许发生的行为。
- **应**：正常情况下要求做到；若允许例外，说明例外条件、责任和补偿方式。
- **可以**：可选能力，不实现也不影响强制要求。

强制性词汇只在确有业务或质量约束时使用。不要把偏好、建议或未确认方案写成“必须”。

### 13.2 需求单元的最小语义

关键需求至少包含：

1. 需求 ID 和目标。
2. 参与者、发生环境、触发条件和前置条件。
3. 输入、处理规则和可观察结果。
4. 相关权限、数据范围、状态变化和副作用。
5. 失败、受限、超时或恢复路径。
6. 证据、决策状态和验收场景。

用户故事可作为目标摘要：`作为<角色>，我需要<能力>，以便<业务结果>`。它不能取代结构化规格。

### 13.3 验收条件

验收条件写“结果”，不规定不必要的技术实现。推荐使用以下任一形式：

- 场景表：角色、前置条件、测试数据、触发动作、可观察结果、异常分支。
- Given / When / Then：适合单一规则和明确状态变化。
- 指标条款：指标名称、基线、目标、统计口径、窗口、数据源、负责人。
- 标准条款：标准名称、版本、条款编号、适用范围、验证方法。

每个 P0 或高风险 `REQ` 至少覆盖主成功路径和一个相关边界；权限类需求覆盖越权访问，批量或异步需求覆盖部分成功 / 重试 / 幂等，迁移需求覆盖失败回退。没有事实依据时不编造测试数据阈值。

一条验收场景尽量只验证一个触发和一个主要结果。以下内容存在时应有独立覆盖：

- 字段长度、格式、文件类型、大小和数量边界；
- 状态变化的时间边界、角色边界和通知结果；
- 每类关键通知的接收人和合并规则；
- 跨组接受与拒绝、批量条件不满足和部分失败；
- 公开回复与内部处理记录等会产生不同业务副作用的动作。

### 13.4 条件性质量要求

- 性能：写操作对象、负载条件、统计口径、目标分位或上限和测量位置。
- 可用性：写服务范围、统计窗口、排除项、降级和恢复目标。
- 可访问性：存在明确目标时，记录 WCAG 版本、级别或具体成功标准与验证方式。
- 安全：存在明确目标时，记录威胁或资产、控制目标、适用标准版本 / 编号和验证方式。
- 隐私与数据保留：写数据类别、使用目的、访问角色、保存期限、删除或匿名化条件。

只写“高性能”“高可用”“符合 WCAG”“满足安全标准”均不通过验收合同。
